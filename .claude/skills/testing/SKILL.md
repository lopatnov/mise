# Testing — плейбук тестирования

*Как* тестировать. Конкретные команды (тест-раннер, запуск приложения) — в `CLAUDE.md`, здесь
только стратегия.

## Когда применять
- Реализована/изменена логика.
- Нужно решить, каким уровнем тестов покрывать изменение.
- Перед мержем — подтвердить, что фича работает.

## Когда НЕ применять
- Тривиальная правка без поведения (опечатка, переименование) — достаточно `build-validator`.

## Пирамида тестов для Mise (снизу вверх — дешевле к дороже)
1. **Unit**. `api/src/**/*.spec.ts` (Jest) — сервисы/guards/маппинги изолированно.
   `web/src/**/*.test.tsx` (Vitest + Testing Library) — компоненты/hooks/store (`authStore.test.ts`
   — пример для Zustand-стора). Быстрые, изолированные, их большинство.
2. **Integration/e2e (backend)**. `api/test/*.e2e-spec.ts` (Jest) — реальный HTTP-запрос против
   поднятого приложения + MongoDB (CI поднимает `mongo:8` как service-контейнер, см. `ci.yml`).
   Для новых эндпоинтов — обязательный уровень, не только unit на сервисе.
3. **End-to-end / браузер**. Немного, только критичные пользовательские потоки (создание рецепта,
   импорт по URL, вход/регистрация) — открой приложение через скилл `run` и проверь вживую, не
   полагайся только на unit-тесты для визуальных/интерактивных изменений.

Все три уровня — зона роли `tester`. Правило экономности: покрывай нужным **минимальным** уровнем,
не гоняй e2e там, где хватает unit.

## Процедура
1. Из задачи выдели проверяемые сценарии, включая граничные/ошибки (валидация DTO, права доступа
   через `JwtAuthGuard`, edge-cases сериализации Mongoose-схем).
2. Выбери уровень(и) по пирамиде.
3. Прогони тесты (`npm test`/`npm run test:e2e` для `api`, `npm run test` для `web` — см.
   Commands Reference в `CLAUDE.md`); для UI — дополнительно проверь в браузере критичный путь.
4. Зелёный билд подтверждает `build-validator` (не дампи вывод тестов в основной контекст).
5. Найденные дефекты — воспроизводимо описать и передать автору кода.

## Признаки хорошего теста
- Проверяет поведение, а не реализацию; имя описывает сценарий.
- Детерминирован (без флака — особенно важно для e2e против реальной MongoDB: чисти состояние
  между тестами, не полагайся на порядок выполнения), независим от других тестов.
- Один тест — одна причина падения.

## Локализация — отдельная проверка, не часть пирамиды
`npm run check:locales` (`web`) — не тест поведения, а структурная проверка (все 32 локали имеют
те же ключи, что `en.json`). Прогоняй после любого изменения UI-строк, отдельно от Vitest/Jest.

## Эскалация
- Тест требует слишком сложного мока / вскрывает нечистую границу ответственности → к `architect`
  (уточнить корректность структуры), а не «подгонять» тест под текущий код.

## Definition of Done
Сценарии покрыты нужным уровнем тестов, тесты детерминированы и проходят, `check:locales` зелёный
при изменении UI-строк, билд зелёный, найденные дефекты переданы.
