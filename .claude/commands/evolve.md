# /evolve — цикл развития (Group Chat)

В отличие от [`/maintain`](maintain.md) (процедурное обновление — один разумный правильный ответ,
дирижёр + точечные специалисты), здесь задача дискуссионная: какие идеи стоят внимания и почему —
ценность именно в столкновении точек зрения. Поэтому `/evolve` — единственное место в проекте, где
используется паттерн **Group Chat**, а не orchestrator-worker. Механика паттерна — в
[`.claude/skills/group-chat/SKILL.md`](../skills/group-chat/SKILL.md), читай его перед первым
запуском этой команды, здесь — только применение к конкретной задаче.

**Результат раунда — GitHub Issues с меткой `idea-radar`, не код и не PR.** Реализация идеи —
отдельное решение пользователя после ознакомления с issue, эта команда её не принимает
автоматически (см. ценность «Гибкость»/«Легальность» в `rules/index.md` и прецедент `tech-radar`
в `/maintain`).

## 0. Контекст раунда (дирижёр, до старта Group Chat)

- Просмотри открытые и недавно закрытые issues с меткой `idea-radar` (через встроенные
  GitHub-инструменты сессии — субагенты доступа к ним не имеют, см. `agents/repo-scout.md`,
  «Важное ограничение окружения», тот же принцип применяется здесь). Не повторяй уже предложенные
  идеи без нового ракурса — если `competitor-scout` находит то же самое, что уже есть в открытом
  issue, это не новая находка для доклада.
- Если `$ARGUMENTS` задаёт область (напр. `import`, `admin`, `i18n`) — раунд фокусируется на ней;
  иначе — свободная тема, `competitor-scout` сам выбирает, что исследовать.

## 1. Group Chat — состав и раунды

Участники (все — sonnet, кроме `architect` — opus, см. `rules/team.md`):

- [`competitor-scout`](../agents/competitor-scout.md) — открывает обсуждение: 3–6 конкретных
  находок из аналогичных проектов (см. «Радар аналогов» в `CLAUDE.md`), с источником (рабочая
  ссылка) и тем, что именно оттуда применимо к Mise.
- [`architect`](../agents/architect.md) — техническая осуществимость по каждой находке (стек
  NestJS/Mongoose/React/Vite, см. `CLAUDE.md`), грубая оценка сложности (S/M/L) и затронутых
  модулей.
- [`skeptic`](../agents/skeptic.md) — намеренно оппонирует: стоимость поддержки, сложность,
  «а точно ли это нужно пользователям Mise» (self-hosted, личное/семейное использование — не
  SaaS-аудитория конкурента).
- [`product-strategist`](../agents/product-strategist.md) — модератор: ведёт очерёдность реплик,
  решает про доп. раунд, синтезирует финальный ранжированный список.

Раунды (дирижёр — единственный, кто видит и передаёт транскрипт целиком в каждый следующий вызов;
роли друг с другом напрямую не связываются — см. `skills/group-chat/SKILL.md`, «Механика»):

1. **Открытие** — вызови `competitor-scout` (без предыдущего транскрипта, свежий research).
2. **Реакция** — сначала `architect` (получает только доклад `competitor-scout`), затем — **после**
   того как его ответ дописан в транскрипт — `skeptic` (получает доклад **и** реакцию `architect`).
   Строго последовательно, не параллельно: `skeptic` явно использует оценку сложности `architect`
   как часть аргумента о стоимости поддержки (см. `agents/skeptic.md`, «С кем консультируюсь») —
   параллельный вызов оставил бы его без этого материала.
3. **(Опционально) Уточнение** — если `product-strategist` на шаге синтеза считает материал
   противоречивым/недостаточным, ещё один круг: конкретный вопрос конкретному участнику с полным
   транскриптом на тот момент. Максимум один такой круг (см. потолок раундов в
   `skills/group-chat/SKILL.md`).
4. **Синтез** — вызови `product-strategist` с полным транскриптом (все реплики всех предыдущих
   шагов) — финальный ранжированный список, формат см. ниже.

Жёсткий потолок — **3 раунда обсуждения** до синтеза (см. `skills/group-chat/SKILL.md`), не
продлевай ради «ещё немного обсудить».

## 2. Выход

`product-strategist` отдаёт дирижёру финальный ранжированный список (2–8 идей за раунд, не
больше — качество важнее количества), каждая идея с 6 полями (формат — в
`agents/product-strategist.md`): название/суть, источник вдохновения, уверенность источника
(подтверждено/интерпретация), сложность (`architect`), возражение `skeptic` (снято или нет),
продуктовая ценность.

Дирижёр заводит по каждой идее отдельный **GitHub Issue** с меткой `idea-radar` (см.
`rules/index.md` — не пишем идеи в файлы репозитория, GitHub Issues — общее место правды, видимое
пользователю без захода в код). Формат issue:

- Заголовок = название идеи.
- Тело = 6 полей синтеза, плюс ссылка на источник вдохновения текстом (не просто «см. выше»).

**Не реализуем автоматически** — issue заводится на согласование с пользователем, ровно как
`tech-radar` в `/maintain`. Если пользователь позже явно просит реализовать конкретную идею из
`idea-radar` — это уже обычная задача, `/evolve` в ней не участвует.

## Периодичность

Настроен реальный периодический запуск: Routine «Mise /evolve (bi-weekly)» — по названию «раз в
две недели», по факту **дважды в месяц по календарным датам** (8 и 22 число, 6:00 UTC), что не
идентично строгому 14-дневному интервалу (разрыв между 22-м и 8-м следующего месяца — от 14 до
17 дней в зависимости от длины месяца). Для целей этого процесса разница не важна (раунд не более
чувствителен к точному дню, чем «примерно раз в две недели», сдвиг на неделю от `/maintain` —
см. `commands/maintain.md` — сохраняется в любом случае), но не путай это с гарантией строгого
интервала при планировании чего-то, для чего разница в 2–3 дня будет иметь значение. Настроено с
`create_new_session_on_fire: true` (эфемерная сессия, каждый firing стартует заново). Заводить
второй такой Routine не нужно; если периодичность нужно поменять — `update_trigger`, не новый
`create_trigger`.

Если настраиваешь заново (напр. Routine удалили) — спроси пользователя перед тем, как заводить
автоматический периодический запуск.

## Definition of Done

Group Chat проведён по механике `skills/group-chat/SKILL.md` (полный транскрипт на каждом ходу,
последовательные вызовы там, где реплика зависит от предыдущей, потолок раундов не превышен),
финальный синтез существует всегда (даже если консенсус не достигнут — разногласие
зафиксировано явно), по каждой идее синтеза заведён GitHub Issue с меткой `idea-radar` и всеми
6 полями формата, ни одна идея не реализована в коде в рамках этого прохода.
