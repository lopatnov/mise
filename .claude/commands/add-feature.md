# /add-feature — скаффолд вертикального среза

Формализует то, что дирижёр и так делает при добавлении небольшой фичи (как `feature/private-cook-log`,
PR #69) — DTO → эндпоинт → сервис → схема → api-клиент → компонент → локали → тесты → билд — в
повторяемую последовательность. Не создаёт новых ролей и не подменяет решения `architect`/
`security-engineer` там, где они уже требуются по таблице `rules/workflow.md` — только задаёт
типовой порядок прохождения фичи через уже существующие роли.

## 0. Классификация и оценка масштаба

Прочитай `$ARGUMENTS` — описание сценария на простом языке.

- **Query или Command?** Используй словарь, который уже есть в стеке проекта (TanStack Query,
  `web/src/api/*.ts`), не изобретай отдельную CQRS-терминологию: чтение без побочных эффектов →
  `useQuery`-сторона (GET-эндпоинт/сервис-метод, без изменения схемы); запись/побочный эффект →
  `useMutation`-сторона (DTO + `class-validator`, POST/PUT/DELETE-эндпоинт, сервис-метод,
  возможно — изменение Mongoose-схемы). Большинство фич — обе стороны сразу (написать и потом
  прочитать написанное).
- **Расширение существующего модуля или новый модуль?** По умолчанию — расширение (см.
  «Architecture» в `CLAUDE.md`: `admin`/`auth`/`recipes`/… уже по одному домену на модуль). Если
  сценарий требует нового модуля или нетривиального изменения формы уже сохранённых документов —
  это попадает в `rules/workflow.md` («Файл/модуль разросся… нужна структурная
  декомпозиция/выбор технологии») — сначала короткий план от `architect`, потом код. Не решай это
  самостоятельно, если есть сомнение.

## 1. Backend-срез (если сценарий трогает данные/API)

DTO + `class-validator` на входе, контроллер-эндпоинт, сервис-метод, изменение
Mongoose-схемы (`*.schema.ts`) при необходимости — по стилю «Backend» в `CLAUDE.md`.

- Небольшая правка — дирижёр делает сам.
- Достаточно крупная изолированная подзадача — `server-developer` (см. `rules/workflow.md`).
- Сценарий касается `auth`/`admin`/`uploads`/`users`/email — эскалируй `security-engineer`, не
  оценивай риск самостоятельно (тот же принцип, что в `agents/server-developer.md`, Boundaries).

## 2. Frontend-срез (если у сценария есть UI)

Метод в `web/src/api/*.ts`, интеграция в страницу/компонент, состояния loading/error/empty для
списков — по стилю «Frontend» в `CLAUDE.md`. Каждая новая видимая строка — через `t('key')`, ключ
добавлен в `en.json` (эталонная локаль).

- Небольшая правка — дирижёр делает сам.
- Достаточно крупная изолированная подзадача (новая страница/сложная интеграция) —
  `ui-developer` (см. `rules/workflow.md`).

## 3. Локали

Если добавлены/изменены UI-строки — `translator` по точному списку новых/изменённых ключей
(остальные 32 локали, `en.json` не трогает). Пропусти, если сценарий чисто backend.

## 4. Тесты

`tester` — полное покрытие сверх happy-path, который уже входит в DoD `server-developer`/
`ui-developer`: edge-кейсы, `test:e2e` для новых эндпоинтов, проверка в браузере для видимых
изменений (скилл `run`, если доступен в сессии). Фича без теста, фиксирующего её поведение, не
считается завершённой (см. `rules/workflow.md`).

## 5. Верификация

`/build` (делегирует `build-validator`) — билд обязан быть зелёным (0 ошибок) перед тем, как
считать скаффолд готовым. Красный вердикт — возврат на шаг 1/2, не игнорировать.

## 6. Changelog (если поведение видно пользователю)

`technical-writer` — запись в `CHANGELOG.md` (`Unreleased`, секция `Added`). Пропусти для чисто
внутренних изменений без видимого эффекта.

## Чего эта команда НЕ делает

- **Не коммитит, не открывает PR, не мержит.** В отличие от `/maintain`/`/evolve` (плановые циклы
  без присмотра между запусками, где мерж — часть DoD), `/add-feature` — инструмент для активной
  сессии разработки: результат остаётся в рабочем дереве на ревью пользователю. Коммит — по
  обычным правилам сессии (только когда пользователь явно попросит).
- Не заменяет `architect`/`security-engineer` — только задаёт типовой порядок обращения к уже
  существующим ролям для одного частого вида задачи (вертикальный срез фичи).

## Definition of Done

- Код реализован по классификации из шага 0, соответствует стилю окружающего кода.
- Тесты добавлены и зелёные (шаг 4).
- `/build` подтвердил зелёный билд (шаг 5).
- Локали синхронизированы, если менялись UI-строки (шаг 3, `npm run check:locales` зелёный).
- `CHANGELOG.md` обновлён, если поведение видно пользователю (шаг 6).
- Ничего не закоммичено и не запушено без отдельного явного запроса пользователя.
