# /add-feature — вертикальный срез фичи

Формализует то, что дирижёр и так делает при добавлении небольшой фичи (как `feature/private-cook-log`,
PR #69): по описанию сценария реализовать backend → frontend → локали → тесты → билд. Это **не**
генерация пустых заглушек — результат должен соответствовать Definition of Done ниже (рабочий код,
тесты, зелёный билд), как у любой другой фичи такого масштаба. Не создаёт новых ролей и не
подменяет `architect`/`security-engineer` там, где они уже требуются по таблице `rules/workflow.md`.

Слои ниже описывают, **что** нужно реализовать — не жёсткий список обязательных стадий, которые
нужно пройти по порядку независимо от сценария. Решение «сделать самому или делегировать» дирижёр
принимает по тому же базовому правилу `workflow.md` («дирижёр делает сам, кроме…»), по каждому
слою отдельно и только если он вообще применим к сценарию. Когда решение — делегировать: вызови
роль с конкретным входом (описание сценария из `$ARGUMENTS` + затронутый модуль/файл) и не считай
слой закрытым, пока роль не подтвердила свой собственный Definition of Done — красный результат
возвращает к этому же слою, а не пропускается молча.

## 0. Классификация и оценка масштаба

Прочитай `$ARGUMENTS` — описание сценария на простом языке. Пустой или состоящий только из
пробелов аргумент — стоп: попроси пользователя описать сценарий, не вызывай ни одну роль и не
трогай файлы.

- **Что меняется?** Сценарий читает данные, меняет их, или и то и другое — большинство фич
  затрагивают обе стороны (записать и затем прочитать записанное). Не навязывай сценарию
  конкретный API-стиль заранее — следуй уже принятым в затронутом модуле паттернам (см.
  «Architecture» в `CLAUDE.md`), не изобретай новый. Изменение Mongoose-схемы/индекса/проекции
  может понадобиться и чисто читающему сценарию (новый индекс/проекция под запрос), не только
  пишущему — оценивай необходимость отдельно, не по тому, «это чтение или запись».
- **Расширение существующего модуля или новый модуль?** По умолчанию — расширение (см.
  «Architecture» в `CLAUDE.md`: `admin`/`auth`/`recipes`/… уже по одному домену на модуль). Если
  сценарий требует нового модуля, затрагивает несколько модулей одновременно, содержит нетривиальную
  бизнес-логику или требует изменения формы уже сохранённых документов — это попадает в
  `rules/workflow.md` («Файл/модуль разросся… нужна структурная декомпозиция/выбор технологии») —
  сначала короткий план от `architect`, потом код. Не решай это самостоятельно, если есть сомнение.

## 1. Backend (если сценарий трогает данные/API)

DTO + `class-validator` на входе, контроллер-эндпоинт, сервис-метод, изменение
Mongoose-схемы (`*.schema.ts`) при необходимости — по стилю «Backend» в `CLAUDE.md`.

- Небольшая правка — дирижёр делает сам.
- Достаточно крупная изолированная подзадача — вызови `server-developer` (см. `rules/workflow.md`).
- Сценарий касается `auth`/инвайтов/`admin`/`uploads`/email/персональных данных — эскалируй
  `security-engineer`, не оценивай риск самостоятельно (тот же перечень, что в базовой таблице
  `rules/workflow.md`, не сужай его).

## 2. Frontend (если у сценария есть UI)

Метод в `web/src/api/*.ts`, интеграция в страницу/компонент, состояния loading/error/empty для
списков — по стилю «Frontend» в `CLAUDE.md`. Каждая новая видимая строка — через `t('key')`, ключ
добавлен в `en.json` (эталонная локаль).

- Небольшая правка — дирижёр делает сам.
- Достаточно крупная изолированная подзадача (новая страница/сложная интеграция) — вызови
  `ui-developer` (см. `rules/workflow.md`).

## 3. Локали

Если добавлены/изменены UI-строки — вызови `translator` по точному списку новых/изменённых ключей
(остальные 32 локали, `en.json` не трогает). Пропусти, если сценарий чисто backend.

## 4. Тесты

Вызови `tester` за полным покрытием сверх happy-path, который уже входит в DoD `server-developer`/
`ui-developer`: edge-кейсы, `test:e2e` для новых эндпоинтов, проверка в браузере для видимых
изменений (скилл `run`, если доступен в сессии). Фича без теста, фиксирующего её поведение, не
считается завершённой (см. `rules/workflow.md`).

## 5. Верификация

`/build` (делегирует `build-validator`) — билд обязан быть зелёным (0 ошибок) перед тем, как
считать фичу готовой. Красный вердикт — возврат на шаг 1/2, не игнорировать.

## 6. Changelog (если поведение видно пользователю)

Вызови `technical-writer` за записью в `CHANGELOG.md` (`Unreleased`, секция `Added`). Пропусти для
чисто внутренних изменений без видимого эффекта.

## Чего эта команда НЕ делает

- **Не коммитит, не открывает PR, не мержит.** В отличие от `/maintain`/`/evolve` (плановые циклы
  без присмотра между запусками, где мерж — часть DoD), `/add-feature` — инструмент для активной
  сессии разработки: результат остаётся в рабочем дереве на ревью пользователю. Коммит — по
  обычным правилам сессии (только когда пользователь явно попросит).
- Не заменяет `architect`/`security-engineer` — только описывает, что нужно реализовать по слоям;
  решение «сам или делегировать» дирижёр принимает по обычному базовому правилу `workflow.md`, не
  по фиксированному списку обязательных стадий этой команды.
- Не генерирует пустые заглушки/TODO — см. Definition of Done: результат должен быть рабочим кодом,
  как у любой другой фичи сопоставимого масштаба.

## Definition of Done

- Код реализован по оценке из шага 0, соответствует стилю окружающего кода — не заглушка/TODO.
- Тесты добавлены и зелёные (шаг 4).
- `/build` подтвердил зелёный билд (шаг 5).
- Локали синхронизированы, если менялись UI-строки (шаг 3, `npm run check:locales` зелёный).
- `CHANGELOG.md` обновлён, если поведение видно пользователю (шаг 6).
- Ничего не закоммичено и не запушено без отдельного явного запроса пользователя.
