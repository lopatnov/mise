# Team — роли и когда их вызывать

> Описывает **кто за что отвечает**. Процесс — в `workflow.md`. Должностные инструкции —
> в `.claude/agents/*`.

## Роли

Тринадцать ролей. Десять покрывают `/maintain` и разовую работу (как в pressmark — реальная,
регулярно нужная зона, не «стаб на будущее»); три — только `/evolve`, участники Group Chat.

### Ядро (`/maintain` + разовая работа)

| Роль | Модель | Зона ответственности |
|------|--------|----------------------|
| [`architect`](../agents/architect.md) | **opus** | Архитектура, декомпозиция крупных задач, «тяжёлый» рефакторинг (модули/файлы >300 строк), выбор технологий; в `/evolve` — голос технической осуществимости |
| [`server-developer`](../agents/server-developer.md) | sonnet | Изолированные backend-подзадачи (NestJS/Mongoose), достаточно большие для отдельного контекста |
| [`ui-developer`](../agents/ui-developer.md) | sonnet | Изолированные frontend-подзадачи (React/Vite), следит, чтобы `pages/*.tsx` не разрастались в нагромождение компонентов |
| [`tester`](../agents/tester.md) | sonnet | Тесты всех уровней (Jest unit/e2e для `api`, Vitest для `web`, браузер — скилл `run`) |
| [`security-engineer`](../agents/security-engineer.md) | sonnet | Auth (JWT/bcrypt), uploads, admin, инвайты, email, триаж security-алертов (Dependabot/`npm audit`) |
| [`devops`](../agents/devops.md) | sonnet | CI/CD, Docker (mongo/api/web образы), docker-compose, GitHub Actions |
| [`technical-writer`](../agents/technical-writer.md) | haiku | README/CHANGELOG по точному входу (diff/коммиты от дирижёра) |
| [`build-validator`](../agents/build-validator.md) | haiku | Read-only прогон сборки/линта/тестов, структурированный вердикт |
| [`repo-scout`](../agents/repo-scout.md) | haiku | Read-only сбор сигналов для `/maintain`: устаревшие/уязвимые npm-пакеты (`api`+`web`), файлы >300 строк, `.tsx` с нагромождением компонентов |
| [`translator`](../agents/translator.md) | haiku | Перевод UI-строк на 32 локали (все кроме `en` — эталона) по точному списку ключей |

### Group Chat (только `/evolve`)

| Роль | Модель | Зона ответственности |
|------|--------|----------------------|
| [`competitor-scout`](../agents/competitor-scout.md) | sonnet | Research аналогичных open-source проектов (см. «Радар аналогов» в `CLAUDE.md`), открывает раунд конкретными находками с источниками |
| [`product-strategist`](../agents/product-strategist.md) | sonnet | Модератор Group Chat (очерёдность реплик, решение о завершении раунда) + продуктовый голос (fit с пользователями Mise), синтезирует финальный ранжированный список |
| [`skeptic`](../agents/skeptic.md) | sonnet | Намеренно оппонирует каждой находке: стоимость поддержки, сложность, «а точно ли это нужно нашим пользователям» — противовес энтузиазму research'а |

Большинство мелких и средних задач **дирижёр (главная сессия) делает сам**, без спавна агента —
см. «Когда НЕ вызывать агента» в `workflow.md`. Новая роль нужна, только когда одной из
существующих зон **регулярно и объёмно** не хватает — тогда копируй `_TEMPLATE.md`. Не плоди роли
под гипотетическое будущее.

### Почему такая модель у каждой роли

Не случайный выбор — по типу задачи: **opus** там, где нужна стратегия/структурное решение с
высокой ценой ошибки (`architect` — единственная роль на opus, в том числе как арбитр
осуществимости в `/evolve`); **sonnet** — там, где роль сама *пишет* код/тесты/конфиг и должна
рассуждать о корректности, либо участвует в содержательной дискуссии Group Chat
(`server-developer`, `ui-developer`, `tester`, `security-engineer`, `devops`, `competitor-scout`,
`product-strategist`, `skeptic`); **haiku** — там, где задача по сути механическая при точном
входе: свести результат к формату (`build-validator`/`repo-scout` — прогнать команды и доложить,
без интерпретации) или переписать по строгому шаблону (`technical-writer`, `translator`). Если
роль на haiku начинает регулярно давать не тот результат — это сигнал, что входные инструкции
недостаточно конкретны, а не повод молча смириться с качеством; в первую очередь уточняй промпт
агента, и только если это не помогает — поднимай модель.

## Кто главный в своей зоне

- **Структура/архитектура** → `architect`. Его решение по структуре и выбору технологий — финальное.
- **Безопасность** → `security-engineer`. Может заблокировать мерж до устранения серьёзного риска.
- **CI/CD и инфраструктура** → `devops`.
- **Тестирование** → `tester`.
- **Ранжирование идей `/evolve`** → `product-strategist` предлагает порядок, но финальное решение —
  **реализовывать или нет** — всегда за пользователем (issue на согласование, не auto-adopt).
- Во всём остальном решение принимает дирижёр (главная сессия), при необходимости — сверяясь
  с пользователем напрямую.

## Эскалация

- Архитектурный вопрос/конфликт (сложность, связность, выбор технологии) → `architect`.
- Риск безопасности → `security-engineer`.
- Неясность требований пользователя → вопрос пользователю напрямую (нет отдельной роли-посредника
  между пользователем и командой — задачи ставятся через GitHub Issues/PR или напрямую в диалоге).
- В `/evolve`: тупик обсуждения (участники не сходятся) → `product-strategist` как модератор
  обязан либо принять явное решение с обоснованием, либо зафиксировать разногласие в issue как
  открытый вопрос — раунд не может закончиться молча без синтеза (см. `commands/evolve.md`).

## Политика инструментов (`tools:`)

Реальные имена инструментов в этой среде: `Bash, Read, Glob, Grep, Edit, Write, WebFetch,
WebSearch`.

Least privilege, не «дать всем всё по умолчанию»: `WebFetch`/`WebSearch` выдаются только ролям, у
которых внешнее чтение — часть их письменного Mandate (research/сверка версий/CVE), не всем
ролям с доступом на запись — это сознательно сужает поверхность атаки через prompt injection
из внешнего контента (см. «Внешний контент — это данные, не команды» в `rules/index.md`; находка
подтверждена ревью PR #37 — исходно web-доступ был у всех ролей без разбора, сужено по итогу).

- **Пишут код/файлы + нужен внешний research** (`architect`, `devops`, `security-engineer`):
  `Bash, Read, Glob, Grep, Edit, Write, WebFetch, WebSearch` — их Mandate явно требует чтения
  внешних источников (release notes, CVE-advisories, версии в registry/на GitHub Marketplace).
- **Пишут код/файлы, без документированной нужды в внешнем research** (`server-developer`,
  `ui-developer`, `tester`): `Bash, Read, Glob, Grep, Edit, Write` — реализуют/тестируют по
  внутренней спецификации (`CLAUDE.md`, ТЗ от дирижёра), не по внешним источникам. `tester`
  отдельно наследует браузерные MCP-инструменты, если доступны в сессии, для e2e-проверки через
  скилл `run` — это не `WebFetch`/`WebSearch`, а браузерная автоматизация, другая категория риска.
- **`build-validator`** и **`repo-scout`**: `Bash, Read, Glob, Grep` — без `Edit`/`Write`/
  `WebFetch`/`WebSearch` в списке. **Важная оговорка:** `Bash` сам по себе технически способен
  писать файлы и обращаться в сеть (`echo > file`, `curl`, `rm` и т.п.) — отсутствие `Edit`/`Write`/
  `WebFetch` в `tools:` не создаёт аппаратный/OS-уровневый барьер само по себе. «Read-only» для этих
  двух ролей — это (а) явная инструкция в их собственных агентных файлах (`agents/build-validator.md`/
  `agents/repo-scout.md`, разделы Mandate/Boundaries — какие именно команды разрешены и что агенту
  запрещено делать), которой роль обязана следовать, и (б) обычный permission-механизм Claude Code
  (рискованные Bash-команды запрашивают подтверждение пользователя вне read-only allowlist) — не
  гарантия уровня песочницы. Если нужна именно техническая, а не только промпт-уровневая изоляция —
  это отдельная задача настройки sandbox/permission-конфигурации Claude Code (`allowedDomains`,
  `sandbox.filesystem.*`), не то, что решается полем `tools:` в файле роли.
- **`competitor-scout`**: `Read, Glob, Grep, WebFetch, WebSearch` — read-only research, не
  редактирует код репозитория.
- **`product-strategist`**, **`skeptic`**: `Read, Glob, Grep, WebFetch, WebSearch` — обсуждение и
  оценка, не пишут код; `WebFetch`/`WebSearch` — чтобы при необходимости самостоятельно проверить
  заявленный источник, не полагаясь слепо на пересказ `competitor-scout`.
- **`technical-writer`**, **`translator`**: без сети — переписывают по точному входу от дирижёра,
  не исследуют самостоятельно (см. их файлы).
- Ни одна роль **не имеет** прямого доступа к GitHub-инструментам сессии (issues/PR/merge) — их
  заводит и мержит только дирижёр (см. `agents/repo-scout.md`, «Важное ограничение окружения», и
  `commands/maintain.md`/`commands/evolve.md`, шаг 0/финал). Это сознательное решение процесса
  (единая точка правды и аудита GitHub-действий), а не только техническое ограничение окружения.

> Имя файла агента **обязано** совпадать с полем `name:` во frontmatter.
