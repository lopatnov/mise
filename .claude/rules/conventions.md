# Conventions — инженерные конвенции

> Веб-нейтральный файл. Стандарты, не зависящие от языка/стека. Конкретные команды
> (форматтер, линтер, тест-раннер) — в `CLAUDE.md`.

## Коммиты

Формат из `CONTRIBUTING.md` проекта: `<type>: <subject>` (без scope в скобках, в отличие от
классического Conventional Commits — сверяйся с реальным форматом репозитория, не с общим
стандартом).

- **type:** `feat`, `fix`, `chore`, `docs`, `test`, `refactor`.
- **subject** — повелительное наклонение, без точки в конце, кратко, на английском.
- Тело — зачем/контекст (по необходимости). Ломающие изменения: `BREAKING CHANGE:` в теле.

Пример: `feat: add recipe duplicate button` · `fix: reject expired session token`.

## Версионирование — SemVer

`MAJOR.MINOR.PATCH`: MAJOR — несовместимые изменения, MINOR — обратимо-совместимые фичи,
PATCH — исправления. До первого стабильного релиза — `0.y.z`.

## Ветки

- `main` — всегда зелёная и релизо-пригодная; `dev` — интеграционная ветка (см. `ci.yml`: CI
  гоняется и на `main`, и на `dev`).
- Рабочие ветки: `feature/<кратко>`, `fix/<кратко>`, `chore/<кратко>`, `docs/<кратко>` (см.
  `CONTRIBUTING.md`).
- Не коммитим прямо в `main`/`dev` в обход PR-флоу.

## Changelog — Keep a Changelog

Секции: `Added`, `Changed`, `Fixed`, `Removed`, `Deprecated`, `Security`. Незарелиженное — в
`Unreleased` в корневом `CHANGELOG.md`, если он есть; если файла ещё нет — заводит
`technical-writer` при первом изменении, требующем записи.

## Качество кода

- Код пишется «как окружающий код»: тот же стиль, нейминг, плотность комментариев.
- Biome (`biome ci`) — **обязателен перед мержем** (read-only проверка, команды — в `CLAUDE.md`).
  Запуск — через `build-validator`, не `format` (мутирующий) в рамках верификации.
- Билд зелёный (0 ошибок), предупреждения просмотрены.
- Ориентир для рефакторинга и код-ревью — Clean Code / Clean Architecture / SOLID (Robert C.
  Martin), не абстрактно, а как конкретная рубрика: см. «Владение качеством кода» в
  `agents/architect.md` (адаптировано под стек проекта). Применяется избирательно к коду, который
  уже привлёк внимание (размер файла, сигнал линтера, ревью диффа) — не формальный чек-лист по
  всей кодовой базе разом.
- Простота важнее «умности» (ценность «Простота» из `index.md`).

## PR-чеклист перед merge

- [ ] Билд зелёный, `biome ci` (`api`+`web`) пройден (`build-validator`).
- [ ] Тесты добавлены/обновлены и проходят — включая `web`-тесты (Vitest), даже если CI их пока
      не гоняет (см. «Известное расхождение» в `CLAUDE.md`).
- [ ] `npm run check:locales` зелёный, если менялись UI-строки/локали.
- [ ] Документация и changelog обновлены при изменении поведения (`technical-writer`).
- [ ] Чувствительные части проверены (`security-engineer`), если затронуты.
- [ ] Замечания сторонних автоматических ревьюеров/сканеров обработаны — несколько настроены на
      уровне организации, не видны в файлах репозитория (см. «Ревью PR» в `rules/index.md` —
      список известных инструментов там неполный, сверяйся с реальными checks PR, не с ним);
      CodeRabbit пропускает черновики, переведи PR из draft, если нужен их прогон до мержа —
      **и сверх этого** проведён наш собственный ревью
      диффа (`architect` со свежим контекстом или явный запрос ревью).
- [ ] Соответствует Definition of Done из `workflow.md`.

Для находок `/evolve` (`idea-radar`) чеклист другой — см. `commands/evolve.md`: там результат
раунда — issue, не PR, и мерж-чеклист не применяется.
