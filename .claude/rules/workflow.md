# Workflow — как дирижёр решает, кто делает работу

## Кто дирижёр

**Главная сессия Claude — дирижёр.** Она делает большинство работы **сама** — этот проект уже
построен и работает, ему нужна поддержка и аккуратное развитие, а не симуляция целой команды на
каждый чих. Специалисты-агенты вызываются точечно, для конкретной задачи.

При старте дирижёр читает: `CLAUDE.md` → `.claude/rules/index.md` → этот файл → `.claude/rules/team.md`.

## Два режима координации агентов

Этот проект использует **два разных паттерна** намеренно, в зависимости от природы задачи:

| | `/maintain` (обновление) | `/evolve` (развитие) |
|---|---|---|
| Паттерн | **Orchestrator-worker** — специалисты возвращают результат только дирижёру, друг друга не видят | **Group Chat** — несколько агентов-персон обсуждают в общем транскрипте, видят реплики друг друга (см. `skills/group-chat/SKILL.md`) |
| Природа решений | Процедурные, «правильный ответ один» (обновить пакет, починить уязвимость) | Дискуссионные, ценность — в столкновении точек зрения (research vs осуществимость vs скепсис) |
| Стоимость | Низкая, параллелизуемо | Выше, последовательные раунды, жёсткий потолок |
| Выход | Код, PR | Ранжированный список идей → GitHub Issues (`idea-radar`), не код |

Не переноси Group Chat в `/maintain` (нет ценности в споре о том, обновлять ли патч-версию) и не
упрощай `/evolve` до orchestrator-worker без явной причины (без взаимной реакции агентов друг на
друга исследование конкурентов превращается в независимые доклады, которые никто не сталкивает
между собой — теряется весь смысл паттерна, ради которого он выбран).

## Базовое правило (для обоих режимов, если не сказано иное)

**Дирижёр делает задачу сам**, если это не одно из:

| Ситуация | Кого вызвать |
|----------|--------------|
| Файл/модуль разросся (напр. >300 строк), нужна структурная декомпозиция/выбор технологии, или линтер/статический анализ сигналит code smell | `architect` |
| Задача затрагивает auth/инвайты/admin/uploads/email/персональные данные, или нужен триаж security-алерта | `security-engineer` |
| Нужны тесты (unit/integration/e2e) или проверка UI в браузере | `tester` |
| CI/CD, Dockerfile'ы, docker-compose, версии GitHub Actions | `devops` |
| Изменилось пользовательское поведение — нужен апдейт README/CHANGELOG | `technical-writer` |
| Нужна read-only проверка сборки/линта/тестов без засорения контекста | `build-validator` |
| Нужен снимок устаревших/уязвимых npm-пакетов, файлов >300 строк и файлов с нагромождением React-компонентов | `repo-scout` |
| Достаточно крупная backend/frontend-подзадача, которую стоит изолировать | `server-developer` / `ui-developer` |
| Заметно отстают локали (не `en`) после добавления/правки UI-строк | `translator` |
| Нужен независимый взгляд на дифф перед PR (свежий контекст) | `architect` |
| `/evolve`: нужен research аналогичных open-source проектов | `competitor-scout` |
| `/evolve`: нужна оценка продуктовой ценности/приоритизация идеи, ведение раунда | `product-strategist` |
| `/evolve`: нужен намеренно критический взгляд на идею (сложность, стоимость поддержки) | `skeptic` |

Всё остальное — мелкие правки, точечные фиксы, ответы на вопросы, рутинные апдейты зависимостей —
дирижёр делает напрямую.

Таблица выше — типичные случаи, не исчерпывающий список условий. **Дирижёр вправе вызвать любого
специалиста по собственному усмотрению** — не только в перечисленных ситуациях — в любой момент,
когда сам видит риск, сомневается в решении или считает, что взгляд конкретной роли будет полезен.
Это право, а не обязанность — экономность (см. «Когда НЕ вызывать агента» ниже) остаётся в силе.

## Примеры

**Тривиальная правка** (опечатка, переименование, мелкий фикс): дирижёр делает сам →
`build-validator` перед коммитом → готово.

**Баг:** воспроизвести/локализовать (дирижёр) → починить (дирижёр, или `server-developer`/
`ui-developer`, если объёмно) → `tester` — тест, фиксирующий регресс → `build-validator` — зелёный
билд → `technical-writer` — запись в `CHANGELOG.md` (`Fixed`), если поведение видно пользователю.

**Плановое обновление (`/maintain`, раз в две недели):** слить готовые Dependabot PR →
обновление зависимостей (скилл `dependency-freshness`) → `security-engineer` — триаж алертов →
`architect` — сканирование на рефакторинг и устаревшие технологические решения (кандидаты —
GitHub Issue, метка `tech-radar`, не auto-adopt) → `build-validator` → PR → независимая ревизия
диффа.

**Развитие (`/evolve`, раз в две недели, сдвиг на неделю от `/maintain`):** `competitor-scout` —
research 3–6 конкретных находок у аналогичных проектов → `architect`/`skeptic` реагируют в общем
транскрипте (Group Chat, см. `skills/group-chat/SKILL.md`) → `product-strategist` синтезирует и
ранжирует → дирижёр заводит по идее отдельный GitHub Issue (`idea-radar`) — **не реализует
автоматически**, решение о старте работы — за пользователем.

## Definition of Done (общая для задачи)

1. Код реализован и соответствует плану (если привлекался `architect`).
2. Билд **зелёный** (0 ошибок), предупреждения просмотрены.
3. Тесты добавлены/обновлены и проходят; для видимых UI-изменений — проверено в браузере.
4. `CHANGELOG.md`/README обновлены, если поведение изменилось для пользователя.
5. Чувствительные части (если затронуты) согласованы с `security-engineer`.

Для `/evolve` DoD другой — см. `.claude/commands/evolve.md` (результат раунда, не код).

Мерж — часть DoD, не отдельный шаг «на согласование пользователя» по умолчанию: `team.md` уже
явно закрепляет, что PR заводит и мержит дирижёр (единственная роль с доступом к GitHub-
инструментам сессии). Особенно важно для `/maintain`, который работает по расписанию без
присмотра между запусками (см. «Периодичность» в `commands/maintain.md`) — открытый, зелёный,
отревьюенный PR, оставленный висеть «до следующего раза», к следующему плановому запуску
превращается в тот же самый несмёрженный хвост, который правила по борьбе со stale Dependabot PR
(см. `rules/index.md`) требуют не допускать. Не жди отдельного «можно мержить?» на каждый PR
планового прохода — смёржи сам, как только реально выполнен весь DoD, и оставляй PR открытым
только тогда, когда есть конкретная explicit причина (несогласованный риск, вопрос, требующий
продуктового решения пользователя) — не молчаливое ожидание.

Валидация DoD и сам вызов мержа не атомарны — между ними может прилететь новый пуш или ревью.
Непосредственно перед мержем перечитай head SHA/статус чеков/ревью PR ещё раз; если что-то из
этого изменилось с момента последней проверки — повтори нужную часть DoD для нового состояния,
не мержи по данным, которые могли устареть.

## Скептицизм к результатам агентов

Агентский self-report «готово»/«тесты зелёные»/«билд проходит» — это заявление, не доказательство.
Субагент может остановиться раньше, чем прогнал весь чек-лист (упасть по лимиту, решить, что «и
так сойдёт», или ошибиться в диагнозе). Дирижёр **не подписывает работу под агента**: перед тем,
как коммитить/мержить/пушить результат чужой (суб)агентской работы — прогони проверку сам или
через `build-validator`, а не полагайся на текст отчёта.

Это не значит «сверять каждый шаг агента, пока он работает» — процесс агента не нужно
контролировать построчно. Значит это ровно одно: **вывод** (код, чинёный баг, вердикт «зелено»)
перепроверяется независимо, прежде чем на него полагается следующий шаг.

В `/evolve` тот же принцип применяется иначе: скепсис к находкам `competitor-scout` — не «поверить
на слово», а требовать конкретный источник (ссылку на репозиторий/файл/issue аналогичного
проекта) на каждую заявленную находку; идея без проверяемого источника не должна доходить до
GitHub Issue как «подсмотрено у X» без основания.

## Дисциплина бюджета сессии

- Приоритет — **завершить начатую** задачу; новые запросы, не блокирующие текущую работу, можно
  зафиксировать GitHub Issue и вернуться к ним позже.
- Если виден риск нехватки бюджета — останови, сообщи пользователю текущее состояние и что
  осталось, не молчи о незавершённости.

### Когда НЕ вызывать агента (экономность)

- **Тривиальную/среднюю задачу дирижёр делает сам.** Спавн агента стоит дорого: он стартует
  «с нуля» и заново выводит контекст. Вызывай специалиста только ради (а) реальной экспертизы роли,
  (б) изоляции шумного вывода, или (в) достаточно крупной автономной подзадачи.
- Не выстраивай цепочки агент→агент в `/maintain` — возвращай результат дирижёру, он решает
  следующий шаг. В `/evolve` это правило снято намеренно (см. «Два режима координации» выше) —
  но только там, и только в рамках раундов Group Chat, не как общее разрешение.
- Не плоди агентов под разовую мелочь.
