# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Optional telemetry via the `@nestjs/observe` SDK, **off by default**: it is registered only when both `OBSERVE_APP_KEY` and `OBSERVE_APP_SECRET` are set, and `OBSERVE_SERVICE_ID` is then required (`api/.env` ships it as `api` with blank credentials). Without credentials the API runs exactly as before.

### Changed

- Upgraded the API to NestJS 12 (`@nestjs/*` 11 → 12, including the CLI, schematics and testing packages). NestJS 12 packages are ESM-only, so the Jest transform now also converts `@nestjs/*` to CommonJS, the same way it already does for `uuid`. Unit tests (223), e2e tests, lint and build all pass. `mongoose` stays held at `~9.9.5` (see #129).

### Security

- Upgraded `react-router-dom` 7.14.0 → 7.18.2, closing 8 known advisories including a high-severity (CVSS 8.1) unauthenticated remote code execution issue in `react-router`'s vendored `turbo-stream` deserialization (GHSA-49rj-9fvp-4h2h) — that specific advisory only affects apps running React Router's Framework Mode, which Mise's frontend doesn't use (it's a plain client-side SPA on Data Mode/`createBrowserRouter`), but the upgrade is applied regardless as routine hygiene.
- Fixed two moderate-severity `qs` advisories (GHSA-x5fp-wj9c-mxmx array-limit bypass, GHSA-4mjr-xmp4-gh2g denial-of-service via attacker-controlled `isBuffer`) — `qs` parses query strings on every incoming API request via Express (`@nestjs/platform-express`); also reachable through `body-parser` and, in tests only, `supertest`'s `superagent`. Not a version pin that needed forcing — all three already declared `qs` ranges wide enough to accept the fix (`6.16.0`); the lockfile just hadn't re-resolved to it yet.
- Fixed a high-severity arbitrary file read / SSRF vulnerability in the email-sending dependency (nodemailer), only patched in version 9.x and later (GHSA-p6gq-j5cr-w38f).
- Fixed a high-severity denial-of-service vulnerability in a transitive dependency of the API docs generator (js-yaml via @nestjs/swagger, GHSA-pm4m-ph32-ghv5).
- Recipe photo uploads now enforce the same image-type restriction (JPEG/PNG/WebP/GIF) already used elsewhere in the app; previously any file type could be uploaded and served back from the app's own origin.
- Bumped `nanoid` (transitive, via `vite`'s `postcss` dependency in `web/`) 3.3.16 → 3.3.18, closing a high-severity denial-of-service issue where custom nanoid generators could loop indefinitely when called with `size: 0` (GHSA-2v37-7h3g-55p8). Build-tooling only — not part of the shipped `web/dist` bundle and not reachable from any Mise code.
- Resolved the long-deferred high-severity `extract-zip` symlink path-traversal advisories (GHSA-jmr9-qjv8-65gv and GHSA-7pqw-9j4j-h8q3) — previously accepted as risk here because no fix existed in the `pa11y-ci@4.x` line this project was pinned to. `pa11y-ci@5.0.0` (released since, pulling in `pa11y@10`/`puppeteer@25`) finally carries a clean dependency tree: `npm audit` now reports 0 vulnerabilities in `web/` where this chain previously contributed most of the list. Verified the major bump itself didn't just trade the advisory for a behavior change — the actual `test:a11y` CI step (`pa11y-ci --config .pa11yci.json`) still passes 4/4 URLs with 0 errors against the real built app; `chromeLaunchConfig` and the rest of `.pa11yci.json`'s config surface are unchanged in `pa11y@10`. Also closes a high-severity `basic-ftp` quadratic-time CPU DoS advisory (GHSA-c475-qrg2-pj4r) that had joined the same chain since the original deferral was written.
- Fixed `PATCH /recipes/:id` (recipe update) accepting its body as `Partial<CreateRecipeDto>` — a TypeScript-only mapped type that erases to plain `Object` in the reflection metadata NestJS's global `ValidationPipe` reads, which made the pipe skip validation (and `whitelist` stripping) entirely for this endpoint. In practice this meant an authenticated recipe owner could mass-assign any field onto their own recipe document via the update body — including fields the API never intends to expose there, such as `authorId`, `photoUrl`, `cookNotes`, or `savedBy` — bypassing every length/type/range constraint (`@MaxLength`, `@IsMongoId`, `@ArrayMaxSize`, `@Min`/`@Max`, etc.) that `CreateRecipeDto` declares. Introduced a real `UpdateRecipeDto` (`PartialType(CreateRecipeDto)`) so the same validation and whitelisting now apply to updates as to creates. Found during security review of the step-photo reassignment fix above, while confirming the new `sourceOrder` field's `@IsInt() @Min(1)` validator actually runs.
- Added `@ValidateNested({ each: true })` to `CreateRecipeDto.ingredients`/`.steps` — without it, `class-validator` never recursed into each ingredient/step object, so none of `IngredientDto`'s or `StepDto`'s own field constraints (including the new `sourceOrder`) were enforced on either create or update, despite the decorators being present in code.
- `GET`/`PATCH /admin/settings` no longer echo the stored SMTP password back to the admin's browser. The endpoint was documented as intentionally returning "full settings including SMTP config" and did so verbatim, meaning every admin page load and settings save round-tripped the plaintext password into the browser's JS state (and, via `RecipeFormPage`-style controlled inputs, its DOM) for no functional reason — the send-email path only ever needs it server-side. Saving settings without retyping the password now correctly leaves the stored value untouched (the response the form was seeded from no longer contains it to accidentally overwrite with `undefined`). Found during independent review of the admin-tabs refactor below.
- Fixed a critical-severity IP-spoofing vulnerability (`proxy-addr`, GHSA-jqcg-44mw-7w3h — IPv4-mapped IPv6 trust-subnet bypass) reachable via `express`'s `req.ip`/`trust proxy` handling in `api`'s production dependency tree (`@nestjs/platform-express` → `express`). `npm audit fix` pulled a transitive patch already permitted by the existing ranges, and a `proxy-addr` entry in `api/package.json` `overrides` now pins the patched floor (`^2.0.8`) because `express` itself only requires `^2.0.7`, which would otherwise let a later lockfile regeneration drop back below the fix. The app never enables `trust proxy`, so the subnet-trust bypass itself isn't reachable today, and `RateLimitGuard` only falls back to `req.ip` when no `X-Forwarded-For` header is present, so the patched version is a baseline, not a fix for rate limiting. Separately, and not addressed by this entry: `RateLimitGuard` keys on the first value of the client-supplied `X-Forwarded-For` header, and `web/nginx.conf` appends to that header rather than replacing it, so a client can rotate the value to sidestep the login/register/forgot-password limit. Tracked in #130.
- Fixed a moderate-severity `fast-uri` host-case-normalization advisory (GHSA-hrr3-gc8f-f4qj), reachable only through `api`'s `@nestjs/cli`/`@angular-devkit` build tooling (dev-only, not shipped).
- Fixed a high-severity `source-map-js` event-loop denial-of-service advisory (GHSA-68fv-2mgg-jv7q) in `web` (build/test tooling only, not part of the shipped bundle), transitive via `sass`/`vite`/`jsdom`'s shared `postcss`/`css-tree` chains.
- Fixed a moderate-severity `joi` prototype-replacement advisory (GHSA-wr44-6hxh-3jwq) in `web`, transitive via `start-server-and-test`'s `wait-on` dependency (used only by the `test:a11y` CI step).
- Deferred (accepted risk) a moderate-severity `sprintf-js` denial-of-service advisory (GHSA-hp3w-g68c-fv3c) in `api`'s dev-only Jest coverage-instrumentation chain (`jest` → `@jest/transform` → `babel-plugin-istanbul` → `@istanbuljs/load-nyc-config` → `argparse`/`js-yaml` → `sprintf-js`). The only fix npm offers downgrades `jest` to `25.0.0`, a 5-major-version regression; `sprintf-js`'s vulnerable path is an unbounded-precision format-string parser only reachable from CLI argument help text this project never passes untrusted input through. Revisit once a non-breaking fix exists upstream.

### Fixed

- Saving a recipe no longer shows an "Unsaved changes. Leave anyway?" prompt on the redirect to the saved recipe. The form cleared its unsaved flag and navigated in the same tick, so the router's leave-guard still saw a dirty form. The existing tests stubbed the guard, which hid it; a new test runs against the real router.
- Importing a second recipe from a URL into the same form no longer saves it with the first import's photo when the second page has no photo; the imported photo is now replaced on every URL import (an "Import from text" never touches it).
- The "unsaved changes" guard stays active for edits made after a save that leaves the form on screen (for example a recipe titled "New", whose page address is the create form's own).
- Importing from a URL no longer fails with `Failed to fetch URL: HTTP 403` on every import after the first until the API is restarted (reported with allrecipes.com). URL imports and photo downloads now use their own HTTP(S) agents with no keep-alive and no TLS session caching: Node's shared agent resumed the previous TLS session on every request after the first, which would make repeat fetches look different from the first one. This was not reproducible against allrecipes.com from CI, so it rests on the "restart fixes it" behavior plus a local check that the shared agent resumes sessions and the new agent does not.
- Recipe list/search pagination no longer accepts an unbounded page size (e.g. `?limit=0` previously returned the entire recipe collection in one response).
- Fixed a bug where viewing a recipe's steps could silently reorder them in a way that persisted incorrectly in some cases (cache mutation during render).
- Fixed duplicate ingredients with the same name not rendering correctly in the recipe detail view.
- Editing a recipe's steps (reordering or deleting one) no longer misattributes previously-uploaded step photos to the wrong step, or leaves orphaned photo files behind for removed steps.
- Editing a recipe's steps no longer drops a step's existing photo when a fresh `externalImageUrl` fetch for that step fails (SSRF block, unreachable host, unsupported MIME type) — the previous photo is now kept instead of being silently cleared and deleted.
- Admin invite creation now validates "expires in (days)" as an integer from 1–30 on both client and server; previously an emptied input coerced to `0` and the server accepted it unchecked, producing an invite that expired immediately.
- Admin settings' SMTP port field can now be cleared back to empty; previously clearing it silently saved `0` because the input coerced an empty value to `0` before the `??` fallback ever saw it.
- Admin Users/Invites/Settings tabs now show an explicit error state when their data fails to load, instead of silently rendering as if the list were empty.
- Copying an invite link now reports failure (e.g. clipboard permission denied) instead of always showing a "Copied!" toast regardless of outcome.
- Icon-only destructive buttons in the admin Users/Invites tabs and the active-tab indicator on the admin page now expose an accessible name/state (`aria-label`, `aria-current`) for screen readers, not just a title tooltip and a CSS class.
